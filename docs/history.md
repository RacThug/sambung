Three seams: **(a) lane isolation** - one `SAMBUNG_E2E_LANE=<n>` derives a whole stack (DB `sambung_e2e_<n>` + web/api ports offset by n) in `e2e-config.ts`; `vite.config` reads `WEB_DEV_PORT`/`WEB_API_PROXY_TARGET` (prod-inert, NOT `VITE_`-prefixed so they never leak into the client bundle; base lane == today's exact values), the web `webServer` passes them - two lanes verified **9/9 green concurrently**, no port/DB clash. **(b) the `PAYMENT_GATEWAY=fake` env seam** - a `createPaymentGateway` factory (mirroring `createMailer`) binds the signature-free `FakePaymentGateway` only on the literal `fake` (trimmed to match the guard) and is set in the e2e api `webServer.env`, so a spec can drive a booking to `confirmed` (fake webhook POST / reconcile-on-read) with no outbound Midtrans call; departs from ADR-0015's "fake out of the DI graph", made safe **structurally** by `validateEnv` refusing `fake` on any process that cannot prove it is a local sandbox (the ADR-0029 fail-fast shape; that refusal was gated on an unset `NODE_ENV` until #193 made the claim true). **(c) two Baseline seed fixtures** the flows can't create at runtime - a known-token staff invite on Bali Breeze/Seminyak for the create-account accept path (sha256-stored, raw token mirrored in `e2e-config.ts`; Flow 5/#172) and a paid-but-lapsed payment (`paid` on an `expired` booking, `handled_at` NULL; the #120 inbox item, Flow 7/#174). **Independently reviewed before merge** (payment-adjacent, boss-fight #4 territory) - two fresh reviewers (Standards + Spec), the Spec reviewer caught **one real blocker fixed red-first**: the seam was built but never switched on in the api `webServer.env`, so the harness would have booted the real Midtrans gateway while the README claimed the fake - a shared-file gap that would also have forced the flow lane to edit shared config. All gates green (26 unit + 75 payment specs, typecheck, lint) and the Docker-gated DoD (two concurrent lanes, the seed fixtures hash-verified against the DB) run locally before merge.
- **E2E flow coverage complete - all 8 flows** (2026-07-24, #168-#175 under umbrella #166; PRs #178-#186 + the #189 sweep): the suite grew **9 → 41 tests** across the 4 projects, every flow a purely additive spec file. Flow 1 guest booking → pay → `confirmed` (drives the #167 fake gateway to a real `confirmed` row, asserts the `wa.me` deeplink, and renders a REAL `booking_no_overlap` 409 as the funnel's own localized copy); 2 owner onboards a property (register → priced unit → a real presigned PUT to Garage → "Ready to publish" → the public page); 3 calendar ops (walk-in / block → cancel → **re-books the same nights** to prove the dates actually freed, not just that the bar vanished); 4 reservations + CSV (reads the downloaded **body**, with the excluded row deliberately in-window so it tests the status filter, not a window artifact); 5 staff invite → accept → scoped access (the wire-level **404-not-403** for an unassigned id - RLS as a real session, by id, which only e2e can prove); 6 channel lifecycle (the no-PII `.ics` assertion made non-vacuous by first creating a confirmed booking carrying name/phone/email/price); 7 operations inbox (dismiss + handle, `describe.serial`, asserting the **ledger is untouched** per ADR-0022); 8 auth/session/i18n (guard + `?next`, silent refresh, workspace switch, locale persistence). Shipped over **4 parallel dispatch runs**, 2 lanes each, every lane **independently reviewed** by a fresh agent fed only the issue + ACs. **Two harness gaps surfaced and were fixed in #178, not worked around**: turbo's strict env-mode pruned the undeclared `SAMBUNG_E2E_*`, so the documented `SAMBUNG_E2E_LANE=n pnpm test:e2e` silently ran on the BASE lane (`passThroughEnv`); and `applyDevBucketConfig` sets the Garage bucket's CORS to `WEB_ORIGIN` only, so a non-base lane's browser upload was refused the preflight (per-lane `WEB_ORIGIN`). **The independent reviews earned their keep by mutation-testing rather than reading**: #185's ledger assertion survived three mutants (flip `payment.status`, flip the booking to `cancelled`, make `dismiss` a silent no-op), but #186's workspace-switch test **passed even when `resetQueries` was degraded to `invalidateQueries`** - the exact ADR-0034 regression that test exists to catch - because auto-retrying matchers converge on the post-refetch state either way; fixed with a held refetch + ONE non-retrying `evaluate` sample, proven red-then-green. Conventions updated where the flows bent them: the README now records the **one** documented exception to "never mutate Baseline rows" (Flow 7 clears the two inbox fixtures, Flow 5 spends the invite - three seeded rows total, read by no other flow), and #189 swept the spec inventory + widened the `funnel-mobile-safari` `testMatch`, which was followed by `\.spec\.ts` and so silently excluded `i18n-persistence.spec.ts` - the one spec asserting localStorage, on the engine where localStorage diverges. Follow-up **#182 was filed and fixed the same day** (#192, decision-log row above): the shared dev Garage bucket's CORS was single-origin and last-writer-wins at bootstrap, so two concurrent lanes both uploading 403'd each other's preflight - reproduced end-to-end before it was touched, since it had been filed from a static reading. Its review then found the defect that mattered more: `storage:doctor`'s CORS probe read only the `access-control-allow-origin` header, and Garage attaches `*` to its **403 refusals** - so a healthy bucket, a wrong-origin bucket and a bucket with **no CORS policy at all** all printed one `[PASS]` line. That is ADR-0029's own instrument blind in its own category, and it is why #182 survived unnoticed; the probe now requires a 2xx as well. **Of the two follow-ups it left, #193 is now closed** (2026-07-24, decision-log row: the guards no longer key on `NODE_ENV` at all - a deployment is recognised by `WEB_BASE_URL`/`STORAGE_PUBLIC_BASE_URL` naming a public host, which sidesteps the inverted `STORAGE_ENDPOINT` check, since Garage-on-VPS is a blessed prod shape where the endpoint IS loopback and the call SUCCEEDS; it also fixed a second inert reader the issue missed, the refresh cookie's `Secure` flag). **#194 is now closed too** (#197): the `channel-lifecycle` "Sync error" assertion spent its 20 s budget on a real `example.invalid` DNS failure (which `getaddrinfo` on the libuv threadpool drags to the smoke-fetch's full 8 s ceiling once the pool is queued behind the suite's bcrypt logins), so it failed under two concurrent lanes and passed in ~2.6 s alone. Fixed by connecting a **private-LAN** feed (`192.168.1.50`) instead: the `ical-fetcher` SSRF guard (ADR-0016) refuses it before any socket, reaching the SAME `error`-status branch with zero I/O - so the guard is now *behaviourally* tripwired (weaken the private-host block and the server really dials it, the status changes, the spec reddens) rather than merely exercised. The one honest cost - nothing in the repo now issues a real outbound `fetch` from `HttpIcalFetcher` - is structural, not a gap: a test HTTP server must live on loopback, which the guard blocks by design, so real-outbound coverage is impossible in-repo without weakening the thing it tests. **Two new follow-ups filed from the #193/#194 reviews**: **#198** (`SAMBUNG_E2E_LANE` isolates the DB + ports but NOT `playwright/.auth` or `test-results/`, so two lanes in ONE checkout race a shared session file whose tokens were minted against a *different* lane's DB - surfacing as plausible-looking 404s misread as bugs; separate worktrees, and thus every dispatch lane, are unaffected) and **#199** (`calendar-booking-ops` failed a *click* under heavy load at two different scenarios across two independent sightings - filed as a lead to establish reproducibility, not a diagnosis). #196 (#193) and #197 (#194) were both independently reviewed to PASS; #196's re-review - after its fix round pulled the SSRF predicate into scope - was completed by the dispatcher in-loop (predicate strictly stronger over a 26-host probe, the `[::1]` fix mutation-proven) when the fresh reviewer hit a session limit, a weaker independence noted for the record on a security-adjacent change.
